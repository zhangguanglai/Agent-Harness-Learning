name: code-review
description: 按清单做一次结构化代码审查，输出「必须改 / 建议改 / 可以忽略」三档
when: 用户要求 review、检查 diff、合并前自查时
requires_tools: bash, read_file, list_dir
---

## 步骤

1. **划定范围**：`git status --short` + `git diff --stat`；没有 git 时按用户指定目录。
2. **逐个文件读**：一次读一个文件，记录 `文件:行号`。
3. **按清单检查**：
   - 错误处理：异常是否被吞、失败路径有没有返回值；
   - 边界条件：空输入、超大输入、并发、超时；
   - 命名与职责：函数是否只做一件事，命名是否说谎；
   - 测试：改动的行为有没有对应断言；
   - 安全：拼接 SQL / 路径 / 密钥硬编码 / 日志泄露。
4. **分级输出**：
   - **必须改**：会导致错误行为或安全事故；
   - **建议改**：可维护性、性能、一致性；
   - **可以忽略**：风格偏好，明确标注「非阻塞」。
5. **验证结论**：能跑测试就跑一次，把命令与结果附在最后。

## 输出格式

```markdown
## 结论
（一句话：可以合并 / 改完再合 / 需要重新设计）

## 必须改
- `src/auth.ts:42` 未处理 token 过期，会导致 401 后死循环

## 建议改
- ...

## 可以忽略
- ...

## 验证
- `pnpm test:unit` → 通过（128 passed）
```

## 注意

- 不确定的地方标注「需要作者确认」，不要猜。
- 只审查 diff 涉及的逻辑，不做无关重构建议。
- 不修改代码，除非用户明确要求「顺手改掉」。
