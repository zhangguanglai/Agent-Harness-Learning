> 代码：[`subagent.py`](../mini_harness/subagent.py)、实验 [`lab06`](../labs/lab06_subagent.py)。

## 1. 子代理的本质：一次带隔离上下文的工具调用

不要把它想成「另一个 AI」。拆开看只有三件事：

```
父 Agent 调用 delegate(goal)
   → 新建一个 Agent 实例（新 messages、新 tracer）
   → 子代理跑完整循环，直到自己停止
   → 只把最终文字（截断后）塞回父的 tool 消息
```

因此「多代理」不需要新协议、不需要消息总线，它就是一个普通工具。
站点里 Claude Code 的定义也是这个意思：子代理在独立上下文里跑完再回报一行结果。

## 2. 为什么需要隔离：上下文污染

三种典型污染：

| 污染 | 例子 | 后果 |
| --- | --- | --- |
| 探索噪音 | 在 3000 个文件里 grep 出 200 条命中 | 主上下文塞满无关路径 |
| 试错残留 | 子任务试了 5 种方案，4 种失败 | 模型被失败路径带偏 |
| 长尾细节 | 读了一个 800 行的配置文件 | 后面几轮都在为它付 token |

子代理把这些都关在自己的上下文里，父会话只拿到「结论 + 关键路径」。

代价也很明确：

- 子代理看不到父会话的中间推理，**必须把 goal 写自包含**；
- 结论有损，父会话无法复核细节（只能再派一次或自己去看）；
- token 总量通常**更高**（多了一份系统提示和独立探索）。

所以判据不是「任务大不大」，而是「这次探索会不会弄脏主上下文」。

## 3. 什么时候派子代理

适合：

- 广度搜索（「在仓库里找出所有调用 `legacy_api` 的地方并分类」）；
- 独立验证（「复现这个 bug，确认是哪个 commit 引入的」）；
- 并行调研（几个目录/几个假设各派一个）；
- 需要「用完即弃」的长上下文任务。

不适合：

- 需要主会话已有上下文的任务（子代理看不到）；
- 一步就能完成的事（派生的开销大于收益）；
- 需要连续多轮与用户交互的任务；
- 高风险写操作（收窄权限后往往做不成，不如主会话逐条审批）。

## 4. goal 必须自包含：写法模板

```
目标：<一句话，可验收>
范围：<哪些目录/文件；不要碰什么>
已知：<父会话已经确认的事实，避免子代理重复探索>
验收：<可运行的命令，或明确的判定标准>
输出：<要回传什么：结论 + 文件:行号 + 风险>
```

反例：「看看这个项目」——子代理不知道看什么、看到什么程度算完。

## 5. 权限与深度：两道边界

```python
child_config = replace(
    self.config,
    mode=self.policy.mode,          # 继承父模式，不能提权
    tool_groups=("core",),          # 工具面收窄：无 shell / 网络 / 记忆 / delegate
    max_turns=min(8, ...),          # 轮次预算更紧
)
```

- **继承模式**：父在 `plan`，子也只能只读；父在 `default`，子的写操作仍走同一个审批人；
- **收窄工具组**：子代理不需要 `bash` 时就不要给；
- **深度上限 1**：子代理的工具组里根本没有 `delegate`，Agent 层再加一道 `depth >= 1` 的防线。

为什么必须限制深度：代理自我复制是指数级消耗，且极难调试。

## 6. 三种多代理形态

| 形态 | 机制 | 适用 | 站点对应 |
| --- | --- | --- | --- |
| 派生（delegate） | 父调子，同步等结论 | 一次性调研、验证 | SubAgents |
| 团队（teams） | 多个长期会话，人做调度 | 跨模块并行开发 | Agent Teams |
| 看板（kanban） | 任务队列 + 多 worker 轮询 | 常驻自动化、批量任务 | Hermes Kanban |

三者的共同点：**上下文隔离 + 明确的任务边界**。
不同点：调度者是人（teams）、父代理（delegate）还是队列（kanban）。

## 7. 并行派生的工程细节

同时派 N 个子代理时，注意：

1. **并发上限**：模型 API 有速率限制，子代理之间会互相抢配额；
2. **结果合并**：父会话要能处理「部分成功」，不要因为一个子代理失败就整体失败；
3. **副作用冲突**：多个子代理改同一文件会互相覆盖——要么只读，要么分区；
4. **成本可见**：每个子代理的 usage 要单独记账（本仓库 `subagent_end` 事件）。

本仓库在父轨迹里记录 `subagent_start` / `subagent_end`（含轮次与 token），
就是为了让「一次任务派了几个子代理、各花了多少」可查。

## 8. 什么时候**不要**用多代理

- 任务本身是串行依赖的（B 必须等 A 的结果）；
- 你需要精确控制每一步（多代理会放大不确定性）；
- 权限边界很敏感（每多一层代理，审计难度上升一层）；
- 上下文隔离不是问题时——直接把活干完更省钱。

一句话：**多代理是上下文管理的工具，不是能力增强的工具。**

## 9. 自测

1. 子代理为什么必须把 goal 写成自包含的？它看不到什么？
2. 派生一个子代理，token 总量通常会变高还是变低？为什么还值得？
3. 子代理的权限为什么继承而不是重置？如果重置会发生什么？
4. 深度上限设成 1 而不是 3，理由是什么？
5. 三个子代理同时改同一个文件，你会怎么设计避免冲突？
