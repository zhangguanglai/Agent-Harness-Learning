# 16 · 实施方案：里程碑、团队与验收

> 配套 [15 技术设计](15-option-c-technical-design.md)。本文回答「谁、在什么时候、交付什么、怎么算完成」。
> 周期按 1 人月 = 20 人日估算，供预算与排期参考。

## 0. 总览

| 阶段 | 周期 | 目标 | 人力峰值 | 关键风险 |
| --- | --- | --- | --- | --- |
| S0 验证 | 2 周 | 证明 DSH 可在容器内被控制面驱动 | 3 | DSH headless/SDK 不可用 |

## 1. S0：两周验证（Go/No-Go）

**目标**：用最小成本证伪「DSH 可以作为服务端运行时」这个前提。

| # | 任务 | 产出 | 验收 |
| --- | --- | --- | --- |
| S0-1 | 容器内跑 `dsh-headless` | Dockerfile + 启动脚本 | 禁网容器内完成一次「列目录+写文件」任务 |
| S0-2 | 写一个 bundle（工具 + 权限预设） | npm 包 | `--dump-config` 能看到自定义工具与 preset |
| S0-3 | sidecar 驱动 SDK：submit/events/cancel | `dsh-worker` 骨架 | 事件顺序正确，取消 3s 内生效 |
| S0-4 | 审批外置 | 临时 HTTP 审批桩 | DSH `ask` → 外部批准 → 任务继续 |
| S0-5 | OTel 与 token 计量 | collector + 面板 | 一次 run 能看到 trace 与 token |

**退出标准**：5 项全过 → 进入 S1；S0-1 或 S0-3 失败 → 暂停，评估降级为自研路线（见 [14](14-harness-platform-selection.md)）。
**产出物**：`spike/` 目录 + 一页结论备忘（含实际耗时与坑）。

## 2. S1：单租户 MVP（8 周，4 个 sprint）

范围：一个领域（建议选「文档审查/报告生成」这类高频、可验收的场景），单租户，内测 20 人。

| Sprint | 主题 | 交付 | 验收 |
| --- | --- | --- | --- |
| S1-1 | 控制面骨架 | Gateway（OIDC 可先 mock）、Orchestrator 状态机、Postgres 表、SSE 转发 | 提交→执行→事件→终态 全链路打通 |
| S1-2 | Worker 与 bundle | worker 镜像、领域 preset、3 个工具（kb.search / artifact.write / doc.render） | 真实任务产出 docx，含引用 |
| S1-3 | 审批与产物 | Approval Service v1、Artifact 版本、前端审批面板 | 提交审批→批准→产物标记正式版 |
| S1-4 | 评测与内测 | 20 条任务集、指标面板、内测反馈闭环 | 成功率 ≥ 70%，P95 提交 < 500ms |

**S1 明确不做**：多租户、计费、私有化、移动端、复杂权限模型。

## 3. S2：多租户 SaaS（10 周）

| 里程碑 | 内容 | 验收 |
| --- | --- | --- |
| M2-1 隔离 | 租户级 namespace/卷/网络策略；租户上下文贯穿事件与检索 | 跨租户访问 0 成功 |
| M2-2 配额与计费 | 并发/日 token/日运行三类配额；usage_ledger 出账 | 超限 429；账单可对账 |
| M2-3 审批工作流 | 双人审批、SLA 升级、IM 通知 | 超时升级可复现 |
| M2-4 审计与导出 | 哈希链、导出包、删除请求（GDPR 类） | 导出包可验签；删除可追溯 |
| M2-5 灰度 | 版本路由表、按租户灰度、一键回滚 | 灰度 5% → 100% 演练通过 |

## 4. S3：领域深化与规模化（12 周）

- 领域模板化：把 preset + skill + 工具组合成「行业模板」，新客户 1 天可上线；
- 性能：worker 预热池、事件批量落库、检索缓存；
- 私有化：Helm chart + 离线镜像 + 许可证；
- 多模型：路由、降级、按任务选模型；
- SLO 与容量：压测 500 并发，建立容量模型与成本模型。

## 5. 团队与分工（RACI）

| 角色 | 人数 | 负责 | 关键交付 |
| --- | --- | --- | --- |
| 平台/控制面 | 2 | Gateway、Orchestrator、Session、K8s | 控制面 API 与稳定性 |
| Worker/DSH | 2 | 镜像、bundle、SDK 适配、升级 | worker 契约与版本升级 |
| 领域工具/知识 | 2 | MCP server、检索、产物模板 | 领域任务成功率 |
| 前端 | 1 | 工作台、审批、产物预览 | 可用性与交互 |
| SRE/QA | 1 | CI/CD、压测、混沌、安全 | SLO 与发布质量 |

决策：技术负责人（1 人，可由平台负责人兼）对架构与版本节奏负责；领域负责人对任务质量负责。

## 6. 工程实践

- 分支：`main` 保护；PR 需 1 人 review + CI 全绿；
- CI：lint、单测、契约测试、镜像构建、SBOM、漏洞扫描；
- CD：staging 自动部署，prod 手动审批；灰度按租户；
- 回滚：镜像 + 路由表双回滚，目标 < 5 分钟；
- On-call：S1 起建立；告警分级（P0 全站不可用 / P1 租户不可用 / P2 任务失败率升）；
- 文档：ADR（每个关键决策一页）、runbook（故障处置）、容量模型。

## 7. 测试策略

| 层 | 内容 | 频率 |
| --- | --- | --- |
| 单元 | 状态机、策略、幂等、事件投影 | 每次提交 |
| 契约 | 事件 schema、worker HTTP、审批回调 | 每次提交 |
| Golden replay | 用录制的 SSE 回放，断言投影与终态 | 每次提交 |
| 集成 | 真 worker + 假模型；真模型 + 单任务 | 每日 |
| 评测 | 领域任务集（20→100 条） | 每日 + 发布前 |
| 混沌 | 杀 worker、断网、DB 抖动、审批服务超时 | 每周 |
| 安全 | 沙箱逃逸、路径穿越、提示注入语料 | 发布前 |

**门禁**：评测通过率低于基线 3 个点 → 阻止发布；P0 缺陷未清零 → 阻止发布。

## 8. 预算

| 项 | 估算 |
| --- | --- |
| 人力 | S0 0.3 人月、S1 8 人月、S2 10 人月、S3 12 人月 ≈ 30 人月（约 6–8 人 × 10 个月） |
| 基础设施（500 并发） | K8s 约 700 vCPU 峰值 + Postgres + 对象存储，按月估算（云厂商差异大） |
| 模型成本 | 按任务基线 × 日活；缓存命中率每提升 10%，成本约降 6–8% |
| 工具/许可 | 可观测、镜像仓库、密钥管理按现有栈 |

## 9. 风险与触发条件

| 风险 | 触发信号 | 应对 |
| --- | --- | --- |
| DSH 升级破坏契约 | 契约测试红 / 事件形状变 | 回滚镜像；adapter 层加兼容 |
| 领域成功率不达标 | 评测 < 70% | 缩场景、加人工复核、换模型 |
| 成本失控 | 单任务超基线 2 倍 | 预算熔断、缓存、模型降级 |
| 隔离漏洞 | 跨租户测试异常 | 立即停灰度、修网络/卷策略 |
| 团队不足 | 连续两个 sprint 延期 | 砍 S2 非核心（移动端、模板市场） |
| 审批成为瓶颈 | 平均等待 > 8h | 分级审批、批量审批、预授权规则 |

## 10. 验收清单（Definition of Done）

**S0**：5 项 spike 全过，结论备忘签字。

**S1**：
- [ ] 内测 20 人，完成 ≥ 200 次真实任务；
- [ ] 成功率 ≥ 70%，提交 p95 < 500ms；
- [ ] 产物可下载、可追溯（版本 + 引用）；
- [ ] 审批闭环，批准人留痕；
- [ ] 回滚演练 < 10 分钟。

**S2**：
- [ ] 跨租户越权 0；
- [ ] 配额与账单可对账；
- [ ] 审计导出可验签；
- [ ] 灰度 5%→100% 演练通过；
- [ ] 500 并发压测通过，P95 达标。

**S3**：
- [ ] 新租户上线 ≤ 1 天；
- [ ] 私有化离线部署成功；
- [ ] SLO 连续 30 天达标；
- [ ] 单位任务成本较 S1 下降 30%。
