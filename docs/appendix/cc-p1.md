## 本册要点

- 把 Claude Code 当"代理循环"而不是补全器来用：观察 → 推理 → 行动 → 反馈这个闭环，既解释了它为何能端到端干活，也解释了它为何会"高效地跑错方向"。
- 效率增益几乎全部来自**上下文组装**环节（原文估算占开发时间 30%～50%）：跨文件、依赖复杂的任务收益最大，写纯函数时反而净亏。
- 权限是 Human-in-the-Loop 设计：不自动 commit、不自动 push、不跳过你的审阅；可调边界在 `settings.json` 的 allow / deny 与目录读写限制里。
- 两个性价比最高的动作：先花 20 分钟写 `CLAUDE.md`（每次会话省掉重复解释背景），再建立"信任但验证"的审阅习惯，否则效率提升会直接变成质量风险。
- 选型口诀：单行补全与微调交给 Copilot / Cursor Tab；跨文件重构、端到端功能、根因分析交给 Claude Code。

## 逐章笔记

### Claude Code 究竟是什么？

- **一句话**：它的基本单元不是"聊天"也不是"补全"，而是 Agent——一个能读代码库、写文件、跑 Shell、操作 Git，并在每轮反馈后自我修正的执行体。

- **机制/要点**：
  1. 三项能力是"交叠"而非"并列"：本地上下文感知（整个代码库、Git 历史、目录结构）、系统级执行权限（写文件、执行命令、操作 Git）、持续会话记忆（跨会话保留项目理解与决策）。单看每一项都不稀奇，交叠后才出现"能理解你的项目 + 能主动动手 + 越用越懂你"的新物种。
  2. 底层是 Agentic Loop：**观察**（读文件、查 Git 历史、搜符号）→ **推理**（定计划：改哪些文件、什么顺序、依赖关系）→ **行动**（写文件、跑命令、装依赖）→ **反馈**（读回改动、跑测试、查类型）。上一轮输出就是下一轮输入，所以"发现报错并自行修复"是这个循环的自然产物，而不是某个附加功能。
  3. 人机分工写进了产品设计：Agent 是执行者，你是决策者，关键操作要你确认。原文的类比是"坐在驾驶座、手握方向盘、但刹车在你脚下的副驾驶"。
  4. 角色迁移：人的时间从"写实现"转向"定需求与验收标准、审产出、做架构权衡、维护项目上下文"。技能重心从"怎么写"上移到"该写什么、为什么"，判断力（问什么、如何评估答案、何时推翻 Agent）成为新的分水岭。
  5. 安全是"可编程的频谱"而非二元开关：`settings.json` 的 allow / deny 列表、目录级读写限制，再叠加 Hooks 在特定操作前触发脚本，构成分层权限。

- **命令 / 配置 / 代码**（循环即 `意图 → 观察 → 推理 → 行动 → 反馈 → 回到意图`）：

  ```json
  {
    "permissions": { "allow": ["Bash(npm test)"], "deny": ["Bash(rm -rf *)"] }
  }
  ```

  > 权限由 `settings.json` 的 allow / deny 列表与特定目录读写限制配置，这一点原文明确；上述片段的具体键名与匹配语法页面未给出（原文未明确），落地前请以官方 settings 文档核对。

- **定位地图**（把工具放回光谱里看差异）：

  | 工具 | 交互模式 | 执行边界 | 上下文范围 |
  | --- | --- | --- | --- |
  | GitHub Copilot | 被动补全 | IDE 内联建议 | 当前文件与相邻上下文 |
  | ChatGPT / Claude.ai | 问答 | 聊天框输出 | 你粘贴进去的内容 |
  | Cursor Agent | 半自主 | IDE 编辑 + 终端 | 当前项目索引 |
  | Claude Code | 完全自主 | 文件系统 + Shell + Git | 整个代码库 + 会话记忆 |

  关键差异不是"能不能写代码"，而是"能走多远"：Copilot 走一步（补一行），Cursor Agent 走一段（跨文件编辑），Claude Code 走全程（实现 + 验证 + 调试）。再往右是 Devin / Factory 这类"云端沙箱 + 异步全自主"的形态，用真实环境隔离换取无人值守。

- **坑与边界**：
  - 单行补全与微调：描述意图的启动成本高于直接手写，得不偿失。
  - 需要 GUI 的操作（拖拽、可视化设计）：终端原生，帮不上忙。
  - 你自己还没想清楚要什么：它擅长执行清晰意图，不擅长替你决定目标，意图模糊时只会"高效地跑错方向"。
  - 合规约束：代码会发送到 Anthropic API，涉密或受审计约束的仓库需先确认数据处理协议（具体条款原文未明确）。

### 为什么 Claude Code 能 10 倍提升开发效率？

- **一句话**："10 倍"不是营销数字，而是一个可拆解的工程命题：收益来自上下文组装、执行自动化、验证循环三处节省的叠加，且高度依赖任务类型。

- **机制/要点**：
  1. **上下文深度**：人类做跨文件任务时，约 30%～50% 的时间花在"上下文组装"上（找接口、追调用、查类型定义、看测试与 Git blame）。Agent 在会话开始就构建全库结构理解，一次读到位；更关键的是它没有跨文件切换的认知损耗，所以复杂重构的耗时可能从"天"降到"小时"。
  2. **工具自主调用**：底层模型可以完全不变，变的是 Agent 能自主完成"执行 → 反馈 → 修正"闭环，人不再充当 AI 与操作系统之间的"人工中继"。乘法效应落在人的上下文切换次数上：10 步操作由 10 次切换变成 1 次。
  3. **持续记忆**：`CLAUDE.md` 是人与 Agent 共同维护的项目记忆，会话启动时自动加载；Memory 把跨会话积累的偏好与模式持久化。原文给出的记忆类型是 user / feedback / project / reference 四类，可用 `memory/` 目录手动编辑、分类、删除。
  4. **多任务并行（SubAgents）**：主 Agent 拆解任务、子 Agent 在各自独立上下文中并行推进，主 Agent 负责集成与一致性校验。收益不是"快 N 倍"，而是把原本串行的阻塞依赖改写为并行。
  5. **竞争判据是"设计中心"而非功能清单**：Copilot 走 Ambient Intelligence（被动、随叫随到）；Cursor Agent 以 IDE 为中心；Claude Code 以终端为中心、权限边界更宽（Git、依赖、起服务）；Aider / Continue 缺生态（Hooks、Skills、SubAgents、MCP）；OpenHands 走云端全自主，恰是"本地优先 + 人在回路"的反面。

- **命令 / 配置 / 代码**：

  ```text
  效率提升 ≈ 上下文组装节省 + 执行自动化节省 + 验证循环节省
  ```

  ```md
  <!-- CLAUDE.md：项目记忆的最小骨架（结构示意） -->
  ## 技术栈与包管理器
  ## 目录结构与模块边界
  ## 编码规范与禁止事项
  ## 常用命令（安装 / 测试 / 构建）
  ```

  > `CLAUDE.md` 会在会话开始时自动加载、`memory/` 目录可手动编辑，这两点原文明确；字段规范与加载优先级页面未展开（原文未明确）。

- **最适合的场景**：
  - 跨文件重构（如 Express 项目 CommonJS → ESM：`require` → `import`、`module.exports` → `export`、`__dirname` → `import.meta.url`，改完跑测试并修残留）。
  - 端到端新功能（装依赖 → 建模块 → 加接口 → 改前端 → 写测试 → 更新文档），途中遇到版本不兼容会尝试替代方案。
  - 无法本地复现的生产 Bug 根因分析（跨文件追调用链，核对超时配置、连接池、中间件顺序）。
  - 零测试、零文档的遗留项目补测试与文档骨架。

- **坑与边界**：
  - "10 倍"必须按任务折算：上下文组装占比低的场景，Agent 的启动与验证开销成为净成本。
  - 收益被审阅成本对冲：审别人的代码可能比自己写更累，审阅习惯没建立时，得到的是质量风险而不是效率。
  - SubAgents 的前提是子任务真的独立；强依赖下并行只会放大集成成本。
  - 训练数据稀疏的深度领域知识不可信，容易产出"看起来合理但错误"的代码；创意/设计探索阶段还没有验收标准，也不适合委托。

- **原文**：https://agent.jeffjade.com/claude-code/core-advantages/

## 自测（3 题）

1. 为什么"本地上下文感知、系统级执行权限、持续记忆"三项必须**交叠**才构成质变？
   提示：缺执行权限只剩建议（等同聊天框），缺上下文只剩盲执行（等同脚本），缺记忆则每次从零开始；三者相乘才是"能理解项目、能动手、越用越懂你"。
2. 任务是"写一个纯函数校验邮箱格式"，用 Claude Code 还是 Copilot？为什么效率公式在这里失效？
   提示：上下文组装 ≈ 0，收益项几乎全部消失，而"描述意图 + 审阅产出"的启动与验证开销变成净成本，所以手写或补全更快。
3. 为什么说 Claude Code 的权限模型不是"信任或不信任"的二选一？
   提示：`settings.json` 的 allow / deny、目录级读写限制、Hooks 前置校验构成连续可调的频谱，可以按仓库、按命令、按操作类型逐级收紧。
